# test-verify｜テスト実行と結果の検証

## 目的・担当範囲

- 承認済み仕様・テストケースと、**実際に実行したテスト結果**を対応付け、何が保証できたか／できていないかを明らかにする。
- リポジトリルートの `AGENTS.md` に従う。本Skillは `MODE` にかかわらず**検証専用**。ソース・テスト・設定・設計書を編集しない（許可されたビルド・テストによる生成物は `AGENTS.md` §2の範囲で扱う）。
- ケースの設計は `test-design`、テストコードの追加は `test-implement`、エラー原因の深掘りは `debug-investigate`、変更差分の品質評価は `self-review` の責務とする。
- **テストが成功したことと、仕様全体を満たしたことは別**と扱う。

## 入力・開始条件

- **検証対象**：機能・WBSタスク・クラス・テストケース・対象ブランチ（分かる範囲）。
- **期待結果の根拠**：要件／基本・詳細設計／承認済みテストケース。実装の現状を期待値の根拠にしない。
- **実行許可**：`RUN=ok` またはユーザーによる明示的なビルド・テスト実行依頼。`MODE=PAIR|DELEGATE` や `SCOPE` の指定だけでは実行できない。
- 実行許可がない場合は、確認可能な既存結果を読み、**実行計画と判定条件だけ**を提示する。別の依頼に許可を持ち越さない。

## 手順

1. **対象版・期待結果・既存の証拠を確認する**
   - `AGENTS.md` §3に従い、現在／対象ブランチ、コミット済みの版、未コミット・未追跡の差分を区別する。別ブランチは読み取っても無断で切り替えない。
   - 関連するテストコード、確定設計、Flyway Migration、設定、過去の結果（ログ等）を必要な範囲で照合する。ログがない過去の「成功報告」は報告者・時点を明示し、今回の実測と区別する。
   - 対象テストが現在のブランチに見当たらなくても、他ブランチの確認前に「存在しない」と決めつけない。
2. **最小の検証範囲を決める**
   - まず対象テスト（例：`./mvnw -Dtest=OrganizationEntityTest test`）、必要なら関連テスト、影響範囲に応じて全体の `./mvnw test`／`./mvnw verify` の順に提案する。広範な実行は理由を説明する。
   - DB制約・外部キー・採番のテストは、対象のFlyway Migration適用済みスキーマを用いるか確認する。`ddl-auto=create` 等の自動DDLだけで保証したと扱わない。
   - JPAの状態確認では、同じEntityへの反映を調べるのか、`flush`・`clear`・再取得後の永続化を調べるのか、検証目的を区別する。
   - TestcontainersにはDocker接続が必要。接続・環境条件を確認するが、コンテナ・DBデータの削除や設定変更は行わない。
3. **許可の範囲内で実行する**
   - `RUN=ok`または明示依頼があり、対象・環境・影響が分かる場合のみ、必要なテスト／ビルドを実行する。
   - 許可のない実行、勝手な依存追加、ユーザーの承認なしの権限緩和・サンドボックス外での再実行、DBのリセットは行わない。環境エラー時は `AGENTS.md` §5に従い選択肢を示して判断を待つ。追加の外部操作や破壊的操作は個別承認を必要とする。
   - 実行前後のGit状態を確認できる場合は確認し、生成物と予期しないファイル変更を区別する。既存の未追跡ドキュメントを保護する。
4. **結果と原因調査を分離する**
   - 実際に実行したコマンド、対象、終了状態、テスト件数・失敗内容をログに基づいて記録する。出力が途切れた場合は成功扱いしない。
   - `PASS`（実行成功）／`FAIL`（テスト・ビルド失敗）／`ENV-BLOCKED`（Docker・権限・接続等で実行不能）／`NOT-RUN`（未実施）を区別する。実行不能を「テスト不合格」とは扱わない。
   - 失敗時は失敗テスト・assertion・例外等の事実を示す。原因の推測は分けて記載し、詳細調査は `debug-investigate` に引き継ぐ。
   - テストを通すための期待値変更、`@Disabled`、既存テスト削除、本番コード修正は行わない。
5. **検証できた範囲と漏れをまとめる**
   - ケースごとに「仕様根拠 → 実行したテスト → 結果 → 保証できる範囲」を結び付ける。
   - 未テストの仕様、異常系、並行処理、外部連携、ブラウザ操作など、対象に関係する重要な未検証項目だけを挙げる。対象外タスクは短く分ける。
   - 追加テストが必要なら `test-design`／`test-implement` に、バグ調査が必要なら `debug-investigate` に引き継ぐ。本Skillでは編集しない。

## 出力形式

- **対象と根拠**：対象ブランチ・コミット、参照テスト・仕様、今回の検証範囲。
- **実行記録**：コマンドと実際の結果（または未実行理由）。必要ならテスト件数や失敗箇所。
- **判断**：確認できた振る舞い／未検証の振る舞い、重要な残課題。
- **次の1手**：最小限の追加確認、または担当Skillへの引き継ぎ。

## 完了条件

- 実行済みと未実施、テスト不合格と環境エラーを混同していない。
- テスト結果が確認可能な証拠に基づき、合格範囲を過大評価していない。
- ファイルやGit履歴を勝手に変更せず、ユーザーが次に何を確認すべきか分かる。
