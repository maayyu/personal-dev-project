# task-plan｜開発タスクの実施計画

## 目的と範囲

- このSkillは**計画の提案だけ**を行う。コード・テスト・設計書・Git状態を変更せず、ビルドやテストも実行しない。
- リポジトリルートの `AGENTS.md` を前提とし、作業モード・SCOPE・秘密情報・Git操作の制約を守る。
- 計画中に `MODE=PAIR` や `MODE=DELEGATE` が指定されても、このSkillだけでは実装を開始しない。
- 最終的な計画・設計判断・優先順位の承認者はユーザーとする。

## 入力

ユーザーの依頼から次を確認する。指定書式は強制しない。

- **対象タスク**：何を実装・調査・テストするか（必須）。
- **完了したい範囲**：Entity単体、Repositoryまで、テストまで等（任意）。
- **前提や制約**：WBSのタスクID、時間、優先順位、対象ブランチ等（任意）。

対象タスクが特定できない場合だけ、最初に1つの質問で確認する。

## 手順

1. **現在地を確認する**
   - `AGENTS.md` §3の参照版ルールに従い、作業ブランチと対象機能の実装ブランチ、関連ファイル・進捗を確認する。
   - ブランチが異なる場合は切り替えず、必要に応じてコミット済み内容を読み取る。確認できた版と未確認の作業ツリー変更を区別する。
   - 未コミット・未追跡ファイルがあっても、削除・整理・移動・stash・commitしない。
2. **根拠を確認する**
   - 必要な範囲だけ、要件・基本設計 `docs/BD/`・詳細設計 `docs/DD/`・WBS `docs/project-management/`・既存コードを参照する。
   - 参照した実在パスとブランチ・コミット（確認できる範囲）、計画の根拠となる仕様・制約を簡潔に示す。
   - 現在のブランチにない資料・コードを、プロジェクト全体で不存在・未確定とはしない。参照版と留保事項は `AGENTS.md` §3に従う。
   - ツールやコマンドによる読み取りが失敗した場合、権限を緩めたり書き込み操作に切り替えたりせず、確認できた情報だけで暫定計画を示す。
3. **タスクを分解する**
   - 現在地から完了条件までを、ユーザーが順番に実施できる3〜7程度の作業に整理する。単純な作業では少なくてよい。
   - 各作業に「目的／実施内容／確認ポイント」を短く付ける。過剰なクラス・文書・タスクを追加しない。
   - 既存WBSに対応する場合、タスクID・順序・責務との整合を確認し、WBSと矛盾する追加作業は提案として分離する。
   - 対象外の関連タスクは「後続作業」として短く示し、今回の実施計画を無断で広げない。
4. **検証と完了条件を決める**
   - 対象に適した検証（例：コード確認、JUnit、Repositoryの実DBテスト）を挙げ、期待する結果を仕様から導く。
   - 実際に検証したかのように書かない。テスト実行はこのSkillの範囲外とする。
   - ユーザー自身が説明できるべき重要な仕組みを1〜3点に絞る。
5. **判断待ちを切り分ける**
   - API・DB・永続化・外部挙動・エラー処理・セキュリティ等の未決事項は、推測で確定しない。
   - 不明点を「作業開始を妨げるもの」と「実装中に確認できるもの」に分ける。重要な確認事項は最大3件にまとめる。
   - 軽微な実装選択は既存規約に沿った推奨案を示してよいが、実装や文書変更は行わない。

## 出力形式

依頼の複雑さに合わせて簡潔に、次の順に提示する。

1. **対象・現在地**：対象タスク、現在／対象ブランチ、確認できた進捗、参照した主なファイルのパスと版。未確認事項は明示。
2. **実施計画**：順番付きの3〜7ステップ（各ステップの目的・作業・確認ポイント）。必要ならWBS ID。
3. **検証・完了条件**：何を確認できれば完了か。未実行のテストは予定として記載。
4. **理解ポイント**：ユーザー自身が説明できるようになるべき点（必要な場合）。
5. **要判断事項・次の1手**：ブロッカー、提案、まず着手する1ステップ。

根拠が不足する場合は**暫定計画**と明記し、確定済みの仕様と推測を混同しない。

## 完了条件

- 現在地・参照根拠・作業順序・検証方法・判断が必要な事項が、ユーザーに分かる。
- ユーザーが次に取り組む1ステップを選べる。
- **ファイルの変更、Git操作、ビルド・テスト実行はしていない。**
