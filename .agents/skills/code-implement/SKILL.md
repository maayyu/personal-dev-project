# code-implement｜設計に沿った実装支援

## 目的・担当範囲

- 1つの明確な実装タスクについて、確定仕様に沿った**最小限のコード**を実装または案内する。
- リポジトリルートの `AGENTS.md` を必ず守る。本Skill自体は編集権限を与えない。
- タスク分解は `task-plan`、テスト観点の網羅的な設計は `test-design`、テストコードの本格的な追加は `test-implement` の責務とし、このSkillで先回りしない。
- 重要な仕様変更・設計変更は提案にとどめ、ユーザーの承認なしに反映しない。

## 入力と開始条件

- **対象機能・目的**：何を実装し、何を満たせばよいか。
- **対象ブランチ**：実装すべきコードが存在するブランチ。指定がない場合は `AGENTS.md` §3に従い、現在のブランチと関連記録から確認する。
- **モード**：指定がなければ `MODE=GUIDE`。
- **編集対象**：`MODE=PAIR`・`MODE=DELEGATE`では `SCOPE=...` が必須。パスはリポジトリ相対で指定。
- **根拠**：関連する確定設計書・仕様・既存コード。文書にない仕様上の判断は勝手に補わない。

## 手順

1. **現在地と変更条件を確認する**
   - `AGENTS.md` §3に従って対象ブランチ・該当コード・既存テスト・周辺規約を確認し、参照したパスと版を示す。
   - GUIDEでは読み取りのみ。PAIR・DELEGATEでは `git status --short` 等を確認し、既存の未コミット・未追跡ファイルを保護する。
   - 現在のブランチに対象コードがない場合、別ブランチのコミット済み内容を切り替えずに確認する。確認範囲外を未実装と断定しない。実際の編集は、ユーザーが許可した対象ブランチ上でのみ行う。
2. **実装根拠と責務を整理する**
   - 関連する `docs/BD/`、`docs/DD/`、実在する決定記録と既存コードを必要な範囲で確認する。
   - 対象クラスの責務・公開される振る舞い・DBマッピング・例外・影響範囲を、関係する範囲だけ整理する。
   - 関連するRepository・DB制約・Service等は必要な影響を簡潔に示すにとどめ、対象外のコード例や作業手順へ広げない。
   - API・DB・永続化・セキュリティ・エラー処理の未決事項、設計との矛盾を見つけたら、重要な判断部分の変更を止めて報告する。既存規約に沿う軽微な内部実装は進めてよい。
3. **作業モードに応じて進める**
   - **GUIDE**：ユーザーが自分で書けるよう、実装順序・必要なポイント・必要なら小さなコード例を**回答内だけ**に示す。ファイル変更・一時ファイル作成・自動修正はしない。
   - **PAIR**：ユーザーの担当部分を尊重し、依頼された部分だけをSCOPE内で編集する。自分の作業範囲を勝手に拡大しない。
   - **DELEGATE**：承認済みの仕様とSCOPEに従い、対象コードだけを最小限変更する。未決の設計判断を必要とする場合は、その部分を実装せず報告する。
   - テスト・文書・Migration・設定・依存関係の変更が必要でも、SCOPEに含まれていなければ変更しない。対象追加が必要な理由を示す。
4. **変更内容を確認する**
   - PAIR・DELEGATEでは変更したファイルと差分を確認し、SCOPE外変更や予期しないファイル作成がないか点検する。
   - 設計との対応、既存機能への影響、破壊的なGit操作や不要なリファクタリングがないことを確認する。
5. **検証状況を明確にする**
   - 変更箇所に見合う最小限の確認方法を提示する。テスト実行が依頼・許可された場合だけ実行する。
   - 実際の実行結果と未実行の検証は分ける。テスト失敗の解消を目的に、期待値・テスト有効性を勝手に変更しない。
   - 失敗や不足がSCOPE外に及ぶ場合、無断で修正範囲を拡大しない。

## 出力

- **GUIDE**：参照根拠、実装の順序、変更候補と理由、ユーザーが実装できる具体的な次の1手、検証方法、判断待ち事項。
- **PAIR・DELEGATE**：変更ファイルと要点、採用理由、検証コマンドと実結果／未実施、SCOPE外に残る課題、理解すべき仕組み（1〜3点）。
- 簡単な修正には短く答え、固定の長文テンプレートを強制しない。

## 完了条件

- 実装対象と設計の根拠が明確で、変更または案内がその範囲に収まっている。
- GUIDEではファイル・Git状態を変更していない。PAIR・DELEGATEではSCOPE外を変更していない。
- ユーザーが次の実装・検証に進める。未確認事項と実際に行った検証を区別できる。
