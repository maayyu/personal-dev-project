# code-understand｜既存コードの理解

## 目的・担当範囲

- 既存コードが**実際に何をしているか**を、処理順序・データ・責務・設計根拠に沿って説明する。
- `AGENTS.md` を前提とする。このSkillは `MODE` にかかわらず**読み取りと説明だけ**を行う。ファイルの作成・編集・削除、Gitの変更操作、ビルド・テスト実行はしない。
- 実装計画は `task-plan`、バグ原因の切り分けは `debug-investigate`、コードの変更は `code-implement` の責務とする。気になる点を見つけても自動修正しない。
- ユーザーがJavaやSpring Bootの仕組みを自分の言葉で説明できるようにする。不要な一般論やファイル全体の逐語解説を避ける。

## 入力

- **対象**：クラス・メソッド・処理・例外・ファイルパス等、理解したいもの。
- **知りたいこと**：処理順序、なぜこの実装か、DBとの関係、呼び出し元など（任意）。
- **対象ブランチ・コミット**：指定がなければ `AGENTS.md` §3に従い確認する。
- **理解の深さ**：概略／行単位／関連レイヤーまで、など（任意）。

対象が特定できない場合に限り、必要な点を1つ確認する。

## 手順

1. **参照版と入口を特定する**
   - `AGENTS.md` §3に従い、現在のブランチ・対象ブランチ・参照したパスと版を区別する。
   - 別ブランチを確認する場合も切り替えず、コミット済み内容を読み取り操作で参照する。未確認の作業ツリー変更を含めて判断しない。
   - 指定された処理の入口（Controller・Service・Repository・テスト等）を探し、対象が存在しないと即断しない。
2. **最小限の範囲で処理を追う**
   - 呼び出し元 → 主処理 → 呼び出し先 → 戻り値・DB更新・例外の流れを、質問に必要な範囲で追跡する。
   - 値の由来、型、状態変化、条件分岐を具体的なメソッド・フィールド名と対応付ける。
   - JPA／トランザクション／Flyway／非同期処理などは、コードと設定で確認できた動作だけ説明する。フレームワークの一般的な挙動は、コードから確認した事実と区別する。
3. **設計との関係を整理する**
   - 必要に応じ `docs/BD/`、`docs/DD/`、関連テストを確認する。実装が正しいという前提で設計を解釈しない。
   - 仕様とコードに食い違いがあれば「確認した差異」として示す。変更案の実装には進まない。
   - 参照できなかったファイル、コードからは分からない実行時の動作、推測を区別する。
4. **理解しやすく説明する**
   - 最初に「この処理は何をするか」を短く述べ、必要に応じ3〜6段階の処理順に整理する。
   - 重要な用語・アノテーション・SQLを、実コードに結び付けて説明する。短い抜粋は必要最小限とする。
   - 既存テストがあれば「コード上で検証する観点」を説明してよいが、成功実績と混同しない。
   - ユーザーが確認すべきポイントを1〜3件に絞る。対象外の機能は深掘りしない。

## 出力形式

依頼に応じて簡潔に、必要な項目を示す。

1. **処理の概要**：何を実現するコードか。
2. **処理の流れ**：入口から結果までの要点。必要なら呼び出し関係や値の変化。
3. **根拠**：参照した主要パス、ブランチ／コミット、関連する設計箇所。
4. **理解ポイント**：重要な仕組みと、自分で確認・説明できるべき点。
5. **未確認・差異**：資料未確認、仕様との相違、推測（ある場合のみ）。

## 完了条件

- 説明した動作を、参照したコード・設定・設計のどこから読み取ったか追える。
- 実装の事実と、推測・一般論・未確認の動作が混同されていない。
- **ソース・テスト・ドキュメント・Git状態を変更していない。**
