# doc-sync｜設計書・開発記録の整合確認と更新

## 目的・担当範囲

- 設計書・決定記録・実装・テスト結果の**確認済みの差分**を整理し、文書間の矛盾・記載漏れ・古い申し送りを必要最小限で修正または提案する。
- `AGENTS.md` の承認済み仕様・作業モード・保護対象ファイルのルールを守る。**コードを正本と決めつけて、仕様や設計を書き換えない。**
- `GUIDE`は更新候補・修正文案のみを回答内に示し、ファイルを編集しない。`PAIR|DELEGATE`で文書編集を行うには、ユーザーの明示依頼と対象文書を含む `SCOPE=...` が必要。
- 変更内容の品質レビューは `self-review`、コード改修は `code-implement`、Waveの完了判定は `wave-wrapup` の担当とする。

## 入力・開始条件

- **更新目的**：どの決定・実装結果・レビュー指摘を反映するか。
- **根拠**：承認済み決定・設計書の該当箇所、確認済みコード／Migration、テスト結果等。
- **対象**：変更してよい具体的な文書パスとブランチ。編集時は `MODE=PAIR|DELEGATE` と `SCOPE=docs/...` 等を明示。
- **実行許可**：必要なビルド・テストを明示依頼または `RUN=ok` で指定する場合のみ。ただし原則として、文書更新のためにテストを再実行せず、既存の検証結果を参照する。
- 決定の承認状態が不明な場合は、正式な文書更新を先行させず、候補として提示する。

## 手順

1. **根拠と対象版を特定する**
   - `AGENTS.md` §3に従い、現在／対象ブランチ、参照コミット、既存文書の版と保留事項を確認する。別ブランチを勝手に切り替えない。
   - 要件・基本設計 `docs/BD/`・詳細設計 `docs/DD/`・実装・Migration・WBS・決定記録を、依頼の範囲で照合する。実在しないパスや文書は創作しない。
   - 変更前の `git status --short` 等で未コミット・未追跡ファイルを把握する。既存の未追跡ドキュメントを無断で上書き・移動・整理・コミットしない。
2. **事実・決定・未決事項を分離する**
   - **決定事項**：ユーザーが承認した仕様・設計判断と、その出典。
   - **確認済み事実**：対象ブランチの実装・DDLや、実際に確認したテスト結果。実装が仕様と一致するかは別に判定する。
   - **提案／未決**：レビュー指摘、改善案、設計との不一致、テスト未実施事項。承認なしに「確定」へ変更しない。
   - 文書間に矛盾がある場合、どこが異なるかと影響を示し、正式な仕様の選択が必要なら更新前にユーザー判断を待つ。
3. **更新する場所と量を絞る**
   - 基本設計は機能・DB・API・画面などの仕様、詳細設計はクラス・処理手順・例外等、WBSは作業と進捗、学習ノートは再利用できる知識と区別する。
   - 既存の見出し・用語・Markdown構成を尊重し、該当節の修正を優先する。重複した新規文書や機械的な学習ノート増殖を避ける。
   - 確定した仕様変更が複数文書に波及する場合、影響先を一覧化する。ただしSCOPE外の文書を勝手に書き換えない。
   - WBSの `.xlsx` 等の別形式や保護対象設定ファイルは、このSkillのMarkdown編集に含めない。更新が必要なら対象と方法を別途確認する。
4. **作業モードに従って反映する**
   - **GUIDE**：変更箇所、変更前後の要旨、具体的な追記・修正文、理由を示すだけ。編集・一時ファイル作成はしない。
   - **PAIR・DELEGATE**：明示された対象ブランチ上で、ユーザーが更新を指示したSCOPE内の文書だけを編集する。現在ブランチが違えば編集を始めない。
   - 設計書は保護対象なので、SCOPEに含まれるだけでなく、**その文書を更新する明示依頼**が必要。コミット済みFlyway Migration、コード、テストは変更しない。
5. **整合性・差分を確認する**
   - 変更後の文書を読み直し、用語、版、参照先、仕様／実装／未確認の表現が一致するか確認する。
   - 変更したファイル・差分・追加した未追跡ファイルを点検する。関係ない文言やレビュー履歴を無断で削らない。
   - 文書反映済み・未反映・判断待ちを分け、必要なら後続の `self-review` または `wave-wrapup` に引き継ぐ。

## 出力形式

- **対象・根拠**：文書パス、参照ブランチ・コミット、対応する承認済み決定／検証結果。
- **同期内容**：変更した節と要旨、またはGUIDEでの変更案。設計との差異と採否。
- **実施結果**：編集したファイル／未編集、確認した差分、未反映の関連文書。
- **要判断・次の1手**：正式な仕様確定が必要な箇所や、追加の更新対象。

## 完了条件

- 根拠のある内容だけを、文書の責務に合う位置へ反映または提案した。
- 設計上の決定と実装済みの事実、テスト実行済みと未検証を混同していない。
- GUIDEは編集なし。PAIR・DELEGATEは承認された文書・ブランチ・SCOPE外に変更なし。
