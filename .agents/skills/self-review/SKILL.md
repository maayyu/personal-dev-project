# self-review｜実装差分の自己レビュー

## 目的・担当範囲

- 指定されたコード・テストの差分について、**仕様への適合性と実装品質**を、具体的な根拠に基づいて点検する。
- `AGENTS.md` を遵守する。このSkillは `MODE=GUIDE|PAIR|DELEGATE` のいずれでも**レビュー専用**。ファイル編集・Git変更操作・ビルド・テスト実行は行わない。
- 実際のテスト実行と結果の確認は `test-verify`、原因の詳細調査は `debug-investigate`、修正作業は `code-implement`／`test-implement`、文書反映は `doc-sync` が担当する。
- 修正案は提案であり、ユーザーによる仕様・実装変更の承認を代替しない。

## 入力

- **レビュー対象**：コミット、変更ファイル、PR相当の差分、WBSタスク・機能。可能なら比較元のブランチ／コミット。
- **観点**：仕様適合、JPA・DB、例外、テスト品質、セキュリティ、保守性など（任意）。
- **参照仕様**：承認済みの要件、基本・詳細設計、決定記録、関連テスト。
- 比較元が未指定なら現在のブランチや対象タスクから候補を確認し、差分の基準が不明な場合は断定を避ける。

## 手順

1. **レビュー対象を固定する**
   - `AGENTS.md` §3に従い、現在／対象ブランチ、比較元、参照したコミット・パスを確認する。対象ブランチを無断で切り替えない。
   - `git diff`、`git show` 等の読み取りで変更箇所を確認し、コミット済みと未コミット・未追跡の変更を区別する。レビューしていない内容まで「問題なし」としない。
   - 以前の変更や既存の問題を、今回の差分が新しく導入した不具合と混同しない。
2. **確定仕様と対応させる**
   - 関連する要件、`docs/BD/`、`docs/DD/`、実在する決定記録、WBSの対象タスクと照合する。
   - 仕様の承認状態が不明、設計書どうしが矛盾、DDLと設計が不一致の場合は、事実と判断待ち事項を分ける。新しい実装が常に正しいとはみなさない。
   - 対象外の後続機能や将来拡張を、今回の完成条件に勝手に追加しない。
3. **影響と不具合リスクを点検する**
   - 対象に応じ、責務分離、入力検証、所有者・認可、例外処理、トランザクション／競合、非同期処理、JPAマッピング、Flyway制約、データ整合性、API互換性を確認する。
   - テストでは、期待結果が仕様由来か、正常系・重要な異常系が不足していないか、assertionが実際の不具合を検出するかを確認する。
   - テスト成功を裏付けるログがなければ実行結果を推測しない。`@Disabled`、期待値弱体化、無意味なassertionがあれば具体的に指摘する。
   - 一般論だけの指摘や、再現・根拠のないバグ断定を避ける。重大なリスクでも証拠不足なら「確認要」とする。
4. **優先度と対応案を整理する**
   - `Critical`：データ破壊・機密漏えい等の重大な問題が確認される場合。
   - `High`：確定仕様への重大な不適合、所有者境界・整合性・主要機能への実害が強く疑われる場合。
   - `Medium`：機能品質、テスト保証、保守性に影響する実質的な改善事項。
   - `Low`：任意の可読性・表現・軽微な改善。
   - 各指摘に対象パス・箇所、根拠、想定影響、最小の修正案または確認方法を付ける。修正が設計判断を伴う場合はユーザー判断待ちとする。
5. **結論と引き継ぎを示す**
   - `重大指摘なし／修正推奨／修正必須／判断保留` などの評価を、**確認できた範囲に限って**示す。
   - テスト実行が必要なら `test-verify`、詳細調査なら `debug-investigate`、変更が必要なら適切な実装Skillへの引き継ぎを提案する。自動修正しない。
   - 外部AIによるレビューを行ったとは主張しない。本Skillの評価と、Claude等の第三者レビューを明確に区別する。

## 出力形式

1. **対象・レビュー範囲**：ブランチ／コミット、比較元、対象ファイルと未確認範囲。
2. **総評**：良い点、問題点と主なリスクを短く。
3. **指摘**：重大度、対象、根拠、影響、改善案。該当なしの重大度は簡潔に。
4. **テスト・仕様の確認状況**：検証済みと未検証を区別。
5. **結論・次の対応**：修正が必要な項目、任意改善、要判断事項。

## 完了条件

- 指摘が実在する差分・仕様に基づき、未確認事項を断定していない。
- 修正必須と好みの改善を分離し、今回のSCOPE外の実装を要求していない。
- コード・文書・Git状態を変更せず、ユーザーが修正要否を判断できる。
