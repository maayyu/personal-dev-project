# test-implement｜仕様に沿ったテストコード実装

## 目的・担当範囲

- 合意されたテストケースを、**既存のテスト基盤と書き方に沿って**実行可能なテストコードへ落とし込む。
- `AGENTS.md` に従う。Skill呼び出し自体は編集許可ではなく、編集には `MODE=PAIR|DELEGATE` と明示的な `SCOPE=...` が必要。
- テストケースと期待結果の設計は `test-design`、実装コードの改修は `code-implement`、広範な実行・結果確認は `test-verify` の担当とする。
- テストを通すためだけに期待値を弱めたり、`@Disabled` を追加したり、本番コードを変更したりしない。

## 入力・開始条件

- **対象**：テスト対象クラス／機能、対象ブランチとテスト対象の作業範囲。
- **仕様根拠**：確定済み設計と、承認されたテストケース（条件・操作・期待結果・対象レイヤー）。
- **作業モード**：省略時 `GUIDE`。編集時のみ `MODE=PAIR|DELEGATE` と `SCOPE=src/test/...` 等の対象パスが必須。
- **実行許可**：テスト実行の明示的依頼、または `RUN=ok` の有無。編集許可と実行許可を混同しない。

期待結果が未確定、またはテスト対象の仕様根拠が見つからない場合は、推測でテストを作らず確認事項を示す。

## 手順

1. **対象ブランチ・既存テストを確認する**
   - `AGENTS.md` §3に従い、ブランチ／コミット・設計書・DDL・テスト基盤・既存テストを必要な範囲で照合する。
   - 現在のブランチに存在しないテストを、プロジェクト全体で不存在と断定しない。別ブランチを読む場合も無断で切り替えない。
   - PAIR・DELEGATEでは、作業前のGit状態を確認し、未コミット・未追跡のファイルを保護する。編集対象ブランチが現在と異なる場合は編集を始めない。
2. **テストケースと実装対象を対応付ける**
   - 各ケースの「条件／操作／期待結果／仕様根拠／テスト層」を確認し、既存テストとの重複と不足を整理する。
   - テスト名、準備データ、検証箇所を選び、1テストで保証する振る舞いを明確にする。
   - Entityの純粋な状態操作は単体テスト、JPAマッピング・Flyway制約・採番・日時は既存の実PostgreSQL／Testcontainers基盤など、**責務に合った層**を用いる。
   - DB制約・外部キー・採番の検証は、対象のFlyway Migrationを適用したスキーマで行う。Hibernateの自動DDL生成（例：`ddl-auto=create`）だけで作られたスキーマに依存していないか確認し、不明なら未確認と報告する。
   - SpringコンテキストやDockerを不要に起動しない。既存JUnit・Spring Test・Mockito等の依存関係と記法を優先し、無断で新しいライブラリを追加しない。
3. **モードに沿って実装する**
   - **GUIDE**：ユーザーが自分で書けるよう、テスト名、Arrange／Act／Assert、準備データ、必要なら短いコード例を回答内に示す。ファイル・一時ファイルを作成しない。
   - **PAIR・DELEGATE**：SCOPEに指定されたテストファイルだけを追加・編集する。既存ケースを消したり、期待結果を実装の現状に合わせて変えたりしない。
   - 追加のテスト用fixture・設定・`pom.xml`・本番コード・Migrationなどが必要なら、SCOPE外は変更せず理由と追加対象を報告する。
4. **テストの品質を点検する**
   - 期待値が仕様由来であり、実行するだけで成功する自明なassertionになっていないか確認する。
   - DBテストは、必要に応じ `flush`・`clear`・再取得で永続化を確認する。制約違反後に失敗したトランザクションで続けて操作しない。テストデータ・トランザクションの独立性を確保する。
   - `@Disabled`・`@Ignore`、テスト削除、assertionの弱体化による成功演出を行わない。仕様に疑義があればテスト実装を止めて報告する。
5. **限定的に検証し、報告する**
   - ユーザーが実行を依頼した場合、または `RUN=ok` の場合のみ、対象テストの実行を行う。例：`./mvnw -Dtest=OrganizationEntityTest test`。実際のクラス名・実行環境に合わせる。
   - Docker／Testcontainersの接続が必要な場合は前提を確認する。環境エラー（例：`bwrap`）とテスト失敗を区別し、権限緩和・構成変更を独断で行わない。
   - テスト失敗の原因がテスト対象の実装・環境側にありそうな場合は、期待値や本番コードを勝手に変更せず、必要に応じ `debug-investigate` への引き継ぎを提案する。
   - PAIR・DELEGATEでは変更ファイル・SCOPE・Git差分を確認し、実際のテスト結果と未実施を分けて報告する。

## 出力形式

- **GUIDE**：対象ケースと仕様根拠、テストを書く順序、既存テストとの違い、必要なコード例、実行方法、未決事項。
- **PAIR・DELEGATE**：変更したテストファイル、追加・補強したケースと保証内容、実行コマンド・実結果／未実行、SCOPE外の課題、理解ポイント。
- 重複ケースを大量に増やさず、まず重要なケースから扱う。対象外のRepository・Service検証は後続作業として短く区別する。

## 完了条件

- 追加・変更した各テストの期待結果が確定仕様と対応し、どの不具合を検出するか説明できる。
- GUIDEではファイル・Git状態を変更していない。PAIR・DELEGATEではSCOPE外を編集していない。
- 成功・失敗・未実行・環境による実行不能を区別し、テスト実装完了とテスト成功を混同しない。
