# debug-investigate｜エラー原因の切り分け

## 目的・担当範囲

- 症状・再現条件・客観的な根拠を集め、**原因の仮説と検証方法**を整理する。
- `AGENTS.md` に従う。このSkillは、`MODE=PAIR`・`MODE=DELEGATE`であっても**原因調査だけ**を担当し、コード・設定・テスト・文書を編集しない。修正作業は `code-implement` 等へ分ける。
- 「エラーの説明」と「原因の確定」を区別する。ログに出た最後の例外名だけで根本原因を断定しない。
- セキュリティ情報が含まれる可能性のあるログ・`.env`・認証設定の値は出力しない。

## 入力

- **症状**：エラーメッセージ、期待動作と実際の動作、失敗した操作。
- **再現条件**：コマンド、操作手順、発生頻度、最後に正常だった状態（分かる範囲）。
- **環境**：実行場所（Dev Container／ホスト）、対象ブランチ、関連モジュール（分かる範囲）。
- **検証許可**：明示的な再実行依頼、または `RUN=ok` があるか。なければテスト・ビルドは実行しない。

## 手順

1. **事実と調査範囲を固定する**
   - 失敗した操作、期待結果、観測結果、再現有無を分ける。まだ再現していないならその旨を記載する。
   - `AGENTS.md` §3に従い、関連コード・テスト・設定のブランチ／コミットと参照パスを明示する。別ブランチへ無断で切り替えない。
   - 既存の未コミット・未追跡ファイルを保護し、履歴破壊・クリーンアップをしない。
2. **根拠を絞って調べる**
   - 必要な範囲のスタックトレース、先行する `Caused by`、失敗したassertion、SQLSTATE、ログ時刻、該当コード・設定・設計を確認する。
   - Javaのコンパイル、Spring起動、JPA／Flyway／DB制約、JUnitの期待値、TestcontainersのDocker接続、Codex実行権限など、まず**どの層で失敗したか**を切り分ける。
   - 秘密情報は原則読み取らず、ログの共有を求める場合も伏せるべき箇所を示す。
3. **仮説と確認方法を整理する**
   - 可能性の高い原因候補を原則1〜3件に絞り、各候補について「支持する事実／反証・不足する証拠／次の確認」を並べる。
   - 仕様・設計とコードが食い違う場合、どちらかを独断で正本化しない。
   - テスト失敗を理由に期待値を変更・削除・無効化しない。原因が未確定なら「原因未確定」と明記する。
4. **安全な追加検証を提案・実行する**
   - まず読み取り操作で確認する。テスト・ビルドの再実行は、ユーザーからの明示的依頼または `RUN=ok` があるときだけ行う。
   - `docker` の広範な操作、DBデータ変更、外部通信、権限緩和、パッケージ追加、設定編集は、テスト許可に含めない。必要なら別途承認を求める。
   - コマンドが `bwrap` 等の環境エラーで実行できなければ、**調査環境の制約**として記録する。実行成功・失敗と、調査対象のテスト成功・失敗を混同しない。同じ失敗を無目的に繰り返さない。
5. **診断結果と引き渡しをまとめる**
   - 確認済みの原因、可能性が高い仮説、未確認事項を分け、必要な場合のみ最小の修正候補を示す。
   - 修正候補が確定仕様やSCOPEに関わる場合はユーザーの判断に委ねる。**このSkill内では編集しない。**

## 出力形式

1. **現象・再現状況**：何が、どの環境で、いつ／どの操作で起きるか。
2. **確認した根拠**：ログの要点、関連コード、ブランチ／コミット。秘密値は含めない。
3. **原因候補**：候補ごとの根拠と確度（確認済み／仮説／反証待ち）。
4. **次の確認手順**：安全なものから、実行許可が必要なものを区別する。
5. **修正の方向性・引き渡し**：原因確定後の対応案、対象外／未確認事項（必要な場合）。

簡単な原因なら短く回答し、仮説の羅列を避ける。

## 完了条件

- 症状と根拠が整理され、次に1つ何を確認すべきか明確になっている。
- 推測や未実行の検証を、確定した原因・成功結果と扱っていない。
- **コード・テスト・設定・文書・Git状態を変更していない。**
